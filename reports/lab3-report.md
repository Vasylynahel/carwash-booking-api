## Реалізований функціонал

Предметна область у мене система запису на автомийку, тому реальний час тут потрібен насамперед у двох місцях: клієнт має одразу дізнаватися про зміну статусу свого запису, а вільні слоти в календарі мають оновлюватися, коли хтось інший забронював час. Методичка описує Socket.io на Node.js, а я використовую відповідник для Python: бібліотеку **python-socketio**. Вона підключається до того самого застосунку FastAPI, тож REST і WebSocket працюють в одному процесі.

**Рівень 1**
- Socket.IO інтегровано в застосунок: точка входу `app.main:application` обробляє шлях `/socket.io`, а решту запитів віддає FastAPI.
- Система кімнат: кожен користувач автоматично потрапляє в `user:{id}`, `role:{роль}` та `all`, а календар підписується на `slots:{дата}`.
- Оновлення в реальному часі для основної сутності: записи (`booking:created`, `booking:status`, `booking:updated`, `booking:deleted`).
- Система сповіщень: таблиця `notifications` зберігає сповіщення, а також вони одразу приходять користувачеві через WebSocket. Є API для читання, позначення прочитаними та видалення.
- Оптимізація запитів: додано індекси під типові запити, прибрано проблему N+1 через `selectinload`, є журнал повільних запитів і скрипт для порівняння планів виконання.
- Розгортання: підготовлено `Dockerfile`, `render.yaml` та інструкцію `docs/DEPLOY.md`. [Вказати, де розгорнуто, і дату перевірки.]

**Рівень 2**
- Автентифікація WebSocket-з'єднань через JWT: токен передається в `auth.token`, без нього чи з refresh-токеном сервер відхиляє з'єднання. Також перевіряється Origin.
- Персоналізовані сповіщення з типами (`booking_created`, `booking_status`, `booking_cancelled`, `master_assigned`) і пріоритетами (`low`, `normal`, `high`). Пакетне надсилання: кілька сповіщень записуються одним запитом.
- Реальний час для всіх основних сутностей: окрім записів, подія `catalog:changed` повідомляє про зміни послуг, постів і правил знижок, а `slots:changed` про зміну вільних слотів на дату.
- Індикатор онлайн-статусу: адміністратор отримує `presence:update`, може запитати список подією `presence:list` або через `GET /api/presence`. Кілька вкладок одного користувача рахуються як одне підключення.
- Відновлення пропущених подій: важливі події отримують наскрізний номер у таблиці `events`, а після перепідключення клієнт передає номер останньої отриманої події (`events:since`) і отримує все, що пропустив. Те саме доступне звичайним запитом `GET /api/events`.
- Комплексна оптимізація: індекси, eager loading, кешування (TTL-кеш з ручним скиданням) і налаштований пул з'єднань.

**Рівень 3 (частково)**
- Ліміт частоти подій WebSocket: не більше 30 подій за 10 секунд від одного з'єднання.
- Метрики й моніторинг: ендпоїнт `/metrics` у форматі Prometheus (запити, тривалість, кількість з'єднань і подій), журнал HTTP-запитів та повільних SQL-запитів, `/health` перевіряє і базу.
- Масштабування: підтримку Redis-адаптера для Socket.IO додано (змінна `REDIS_URL`), а налаштування автомасштабування описано в `docs/DEPLOY.md`.
- Детальна документація WebSocket API: `docs/WEBSOCKET.md` з усіма подіями, кімнатами, форматами, кодами помилок і прикладом клієнта.
- Фонові завдання (прибирання старих подій, автоматичний перерахунок знижок) реалізовано простими циклами asyncio, а не повноцінною чергою.
- Не реалізовано: окрема черга задач (Celery чи аналог) та кешування в Redis. Кеш зараз у пам'яті процесу.

**Власна функція: автоматичні «тихі години»**

У лабораторній 2 адміністратор сам задавав правила знижок. Тепер система вчиться на історії записів: для кожної пари «день тижня × година» вона рахує, яку частку часу пости були зайняті за останні тижні (це дані для теплової карти завантаженості). Година з низькою завантаженістю вважається тихою, і для неї пропонується знижка: чим тихіше, тим більша, до 15%. Сусідні тихі години зливаються в один блок («Вівторок 13:00–17:00 −10%»). Адміністратор переглядає пропозиції та застосовує їх однією дією, а з увімкненою опцією це відбувається автоматично раз на добу. Ручні правила мають пріоритет над автоматичними, тож адміністратор завжди може перекрити рішення системи. Клієнт бачить знижку у списку слотів, а коли хтось змінює правила чи бронює час, слоти оновлюються наживо.

## Ключові фрагменти коду

**1. Автентифікація WebSocket-з'єднання (`app/realtime/handlers.py`).** Токен перевіряється під час підключення, а користувач потрапляє в кімнати за своєю роллю.

```python
@sio.event
async def connect(sid, environ, auth):
    token = auth.get("token") if isinstance(auth, dict) else None
    if not token:
        raise ConnectionRefusedError("unauthorized")
    try:
        payload = decode_token(token, "access")
    except AppError:
        raise ConnectionRefusedError("unauthorized") from None

    user = await anyio.to_thread.run_sync(_load_user, int(payload["sub"]))
    if user is None:
        raise ConnectionRefusedError("unauthorized")

    await sio.save_session(sid, {"user_id": user["id"], "role": user["role"], "exp": payload["exp"], "slots": []})
    for room in user["rooms"]:
        await sio.enter_room(sid, room)
```

Токен має обмежений термін дії, тому при кожній вхідній події сервер перевіряє `exp`. Коли токен спливає, клієнт отримує `auth:expired`, оновлює токен через `/api/auth/refresh` і підключається знову.

**2. Міст між REST і Socket.IO (`app/realtime/publisher.py`).** Ендпоїнти FastAPI виконуються в робочих потоках, а Socket.IO працює в циклі подій, тому розсилка йде через `anyio.from_thread`. Якщо розсилка не вдалась, основна операція не ламається: запис уже збережено.

```python
def emit(event, data, rooms, db=None, persist=False):
    rooms = list(dict.fromkeys(rooms))
    try:
        ids = {room: None for room in rooms}
        if persist and db is not None:
            ids = dict(event_store.store(db, rooms, event, data))
        for room in rooms:
            anyio.from_thread.run(_emit, event, {"id": ids[room], "data": data}, room)
    except Exception:
        log.exception("Не вдалося розіслати подію %s", event)
```

**3. Відновлення пропущених подій (`app/realtime/events.py`).**

```python
def fetch_since(db, rooms, since, limit=None):
    limit = min(limit or settings.replay_limit, settings.replay_limit)
    rows = db.scalars(
        select(Event).where(Event.room.in_(rooms), Event.id > since).order_by(Event.id).limit(limit + 1)
    ).all()
    has_more = len(rows) > limit
    return [serialize(r) for r in rows[:limit]], has_more
```

Подія зберігається з наскрізним номером, а клієнт запам'ятовує останній отриманий. Запит на `limit + 1` рядків дозволяє дізнатися, чи є ще події, без додаткового підрахунку.

**4. Пакетне надсилання сповіщень (`app/services/notification_service.py`).**

```python
def notify_many(db, drafts):
    rows = [Notification(user_id=d.user_id, type=d.type, message=d.message,
                         priority=d.priority, booking_id=d.booking_id) for d in drafts]
    db.add_all(rows)
    db.commit()
    for n in rows:
        publisher.emit("notification", payload(n), [f"user:{n.user_id}"])
    return rows
```

Усі сповіщення від однієї дії (наприклад, скасування запису: клієнту, майстру, адміністраторам) записуються одним запитом і однією транзакцією, а потім розсилаються.

**5. Розрахунок тихих годин (`app/services/analytics_service.py`).** Запис розкладається по годинах, а завантаженість рахується як частка зайнятого часу.

```python
capacity = max(bays, 1) * 60 * weeks   # хвилин, які пости могли б відпрацювати в цю годину за період
load = min(busy.get((weekday, hour), 0.0) / capacity, 1.0)

def discount_for_load(load):
    threshold = settings.auto_quiet_threshold          # 0.30
    if load >= threshold:
        return 0
    raw = settings.auto_discount_max * (1 - load / threshold)
    return int(math.floor(raw / step + 1e-9) * step)
```

Дрібниця, на якій я зловила помилку під час тестів: `15 * (1 - 0.2/0.3)` через похибку чисел із плаваючою комою дає 4,999…, і знижка 5% зникала. Тому додано невелику поправку `1e-9`.

**6. Захист від хибних висновків.** Якщо історії записів мало, майже всі години здаються «порожніми», і система запропонувала б знижки на весь тиждень. Тому, поки записів менше за `AUTO_PRICING_MIN_BOOKINGS` (30), пропозицій немає, а застосування нічого не змінює.

```python
occ = compute_occupancy(db, weeks)
if not occ.enough_data:
    return occ, []
```

## Висновки

У цій лабораторній я додала до серверної частини реальний час, і найбільше з нього зрозуміла, що сама розсилка подій найпростіша частина. Складнощі з'являються навколо неї: хто має право підключитися, що відбувається, коли токен спливає посеред з'єднання, і як клієнт відновлює стан після обриву. Для цього у проєкті є журнал подій із номерами, а ті події, що журналу не мають (слоти, каталог), клієнт просто перезапитує через REST. Окремо розібралась, чому сповіщення мають жити в базі даних, а не лише летіти через WebSocket: користувач, який був офлайн, побачить їх після входу.

Автоматичні тихі години стали логічним завершенням ідеї з другої лабораторної: замість того, щоб адміністратор вгадував, коли знижка потрібна, система бачить це в історії записів. Тут важливим виявився захист від малої кількості даних, а також правило, що ручні правила завжди сильніші за автоматичні.

Автоматичні тести (71) охоплюють і справжній WebSocket: підключення, кімнати, онлайн-статус, відновлення подій, термін дії токена, ліміт подій, перевірку Origin. Тести написано проти справжнього сервера, який запускається в окремому потоці.

З обмежень: кеш, онлайн-статус і ліміти запитів зберігаються в пам'яті процесу, тому при кількох копіях сервера вони показуватимуть лише частину картини. Підтримку Redis для Socket.IO налаштовано, але на справжньому Redis я її не перевіряла. Фонові завдання працюють як прості цикли, а не як окрема черга задач. Тести йдуть на SQLite, тому поведінку блокування рядків у PostgreSQL перевірено лише на рівні коду. Для навчального проєкту цього достатньо, а для промислового навантаження ці місця потрібно було б переробити.
