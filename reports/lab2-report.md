## Реалізований функціонал

Цю лабораторну я виконувала на тому самому проєкті, що й першу: серверна частина вебсервісу запису на автомийку та детейлінг на FastAPI. Методичка описує Node.js, Express і Prisma, тому я знову використовувала відповідники з Python: залежності FastAPI замість middleware Express, PyJWT замість `jsonwebtoken`, `argon2-cffi` замість пакета `argon2`, Swagger, який FastAPI генерує сам, а `pytest` замість `node:test`.

**Рівень 1**
- Реєстрація користувачів із валідацією (формат email, пароль від 8 символів, телефон у форматі `+380…`). Самореєстрація завжди створює клієнта: поле ролі у запиті відсутнє, тому «зареєструватися адміністратором» не вийде. Майстрів і адміністраторів заводить адміністратор через `POST /api/users`.
- Паролі хешуються за допомогою Argon2id, а хеш не потрапляє у відповіді API.
- Автентифікація на JWT: короткоживучий access-токен (15 хвилин) і refresh-токен (7 днів), підписані двома різними секретами.
- Перевірка автентифікації реалізована залежністю FastAPI `get_current_user`, яка є відповідником middleware з методички.
- Три ролі: клієнт, майстер, адміністратор. Авторизація виконується залежністю `require_roles(...)`, а також перевірками «чий це ресурс» усередині ендпоїнтів.
- Пагінація (з першої лабораторної) і Swagger: у ньому з'явилася кнопка Authorize, тож захищені ендпоїнти можна пробувати прямо в документації.

**Рівень 2**
- Файловий сервіс: завантаження, перегляд, заміна вмісту й видалення. Перевіряються розширення, заявлений MIME-тип, розмір (до 5 МБ) і «магічні байти» вмісту. Файл можна прикріпити до автомобіля.
- Пошук і фільтрація: користувачі, автомобілі, послуги, записи й журнал дій мають фільтри та пошук, а видимість обмежується правами.
- Зміна пароля (`POST /api/auth/change-password`).
- Refresh-токени з ротацією та відкликанням. У базі зберігається лише SHA-256 хеш токена.
- Автоматичні тести ендпоїнтів автентифікації та прав доступу.

**Рівень 3 (частково)**
- Журнал дій користувачів: таблиця `audit_logs`, куди потрапляють входи (в тому числі невдалі), реєстрації, зміни пароля, створення й зміни записів, послуг, правил знижок, файлів. Адміністратор переглядає журнал з фільтрами за користувачем, дією та сутністю.
- Обмеження частоти запитів: загальний ліміт на IP-адресу й суворіший для входу та реєстрації. Після перевищення сервер відповідає 429 із заголовком `Retry-After`.
- Завантаження кількох файлів одночасно за принципом «усе або нічого».
- Складніша модель дозволів: окрім ролей, є перевірки власника ресурсу. Клієнт працює лише зі своїми автомобілями й записами, майстер бачить призначені йому записи й може лише розпочати або завершити роботу, а клієнт може лише скасувати власний запис.
- Не реалізовано: відновлення пароля через email, двофакторну автентифікацію та вхід через соцмережі. Їх я залишила поза обсягом цієї роботи.

**Власна функція: «розумні ціни»**

Окрім завдань методички, я заклала в проєкт те, що відрізняє мій сервіс від звичайних систем запису: знижки на тихі години. Адміністратор через `/api/pricing-rules` задає правила (діапазон годин, день тижня або щодня, знижка до 50%). Далі система сама показує клієнту ціну зі знижкою у списку вільних слотів, застосовує її при створенні запису та зберігає розмір знижки в самому записі. Це логічно спирається на лабораторну: керування правилами доступне лише адміністратору, а перегляд слотів із цінами публічний.

У третій лабораторній я додам автоматичний розрахунок тихих годин за історією завантаженості постів і оновлення слотів у реальному часі.

## Ключові фрагменти коду

**1. Автентифікація й авторизація (`app/core/auth.py`).** Користувач дістається з access-токена, а роль береться з бази даних, а не з токена. Завдяки цьому блокування користувача чи зміна його ролі діють одразу, не чекаючи завершення токена.

```python
def get_current_user(db: DbSession, token: Annotated[str | None, Depends(oauth2_scheme)]) -> User:
    if not token:
        raise UnauthorizedError()
    payload = decode_token(token, "access")
    user = db.get(User, int(payload["sub"]))
    if user is None or not user.is_active:
        raise UnauthorizedError("Обліковий запис недоступний")
    return user


def require_roles(*roles: UserRole):
    def checker(user: CurrentUser) -> User:
        if user.role not in roles:
            raise ForbiddenError("Недостатньо прав для виконання цієї операції")
        return user
    return checker


AdminUser = Annotated[User, Depends(require_roles(UserRole.ADMIN))]
```

В ендпоїнті достатньо вказати тип параметра (`admin: AdminUser`), і маршрут стає захищеним.

**2. Ротація refresh-токенів і виявлення викрадення (`app/services/auth_service.py`).**

```python
stored = db.scalar(select(RefreshToken).where(RefreshToken.token_hash == hash_token(refresh_token)))
if stored is None:
    raise UnauthorizedError("Недійсний refresh-токен")

if stored.revoked_at is not None:
    # відкликаний токен пред'явили вдруге: схоже на викрадення
    revoke_all(db, stored.user_id)
    raise UnauthorizedError("Недійсний refresh-токен")

stored.revoked_at = datetime.now(UTC)
db.commit()
return user, issue_tokens(db, user)
```

Кожне оновлення видає нову пару токенів, а попередній refresh-токен стає недійсним. Якщо ним скористаються ще раз, скасовуються всі токени користувача і йому доводиться входити заново.

**3. Перевірка завантажених файлів (`app/services/file_service.py`).** Ім'я файлу й MIME-тип надходять від клієнта і їх легко підробити, тому додатково перевіряється початок вмісту. Файл на диску отримує згенероване ім'я, а оригінальне не використовується як шлях.

```python
if ext not in ALLOWED:
    raise BusinessRuleError(...)
if upload.content_type != ALLOWED[ext]:
    raise BusinessRuleError("MIME-тип файлу не збігається з його розширенням")

head = upload.file.read(16)
upload.file.seek(0)
if not _magic_matches(ext, head):
    raise BusinessRuleError("Вміст файлу не відповідає заявленому типу")

stored_name = f"{uuid.uuid4().hex}{ext}"
```

Розмір контролюється під час запису частинами: якщо ліміт перевищено, недозавантажений файл видаляється з диска.

**4. «Розумні ціни» (`app/services/pricing_service.py`).**

```python
def best_rule(rules, local_start):
    t = local_start.time()
    matching = [
        r for r in rules
        if (r.weekday is None or r.weekday == local_start.weekday())
        and r.start_time <= t < r.end_time
    ]
    return max(matching, key=lambda r: r.discount_percent, default=None)


def apply_discount(base: Decimal, percent: Decimal) -> Decimal:
    return (base * (Decimal(100) - percent) / Decimal(100)).quantize(CENT, rounding=ROUND_HALF_UP)
```

Знижки не складаються: якщо слот потрапляє під кілька правил, діє найбільша. Кінець діапазону не входить, тому правило 13:00–17:00 діє для слота 16:30, але не для 17:00. Суми рахуються типом `Decimal` з округленням до копійок, а не `float`.

**5. Обмеження частоти запитів (`app/core/rate_limit.py`).**

```python
def _check(key: str, limit: int, window: int) -> None:
    now = time.monotonic()
    hits = _hits[key]
    while hits and hits[0] <= now - window:
        hits.popleft()
    if len(hits) >= limit:
        retry_after = int(window - (now - hits[0])) + 1
        raise TooManyRequestsError("Забагато запитів, спробуйте пізніше",
                                   headers={"Retry-After": str(retry_after)})
    hits.append(now)
```

Це лічильник «ковзного вікна» в пам'яті процесу для кожної IP-адреси. Він підходить для однієї копії сервера. Якщо серверів буде кілька, лічильники доведеться переносити в Redis, що передбачено в лабораторній 3.

## Висновки

У цій лабораторній я перетворила відкритий API з першої роботи на захищений сервіс. Тепер користувачі реєструються й входять, кожна дія перевіряється за роллю та належністю ресурсу, а в журналі лишається слід усіх важливих дій. Найцікавішим виявилося питання токенів: короткий термін життя access-токена не дає ним зловживати, а refresh-токени з ротацією та виявленням повторного використання дозволяють відкликати доступ без очікування завершення терміну. Окремо розібралася, чому роль краще перевіряти за базою даних, а не за токеном, і чому помилку «невірний поточний пароль» не варто повертати як 401: клієнтська частина на цій відповіді завершує сесію.

Під час тестування я знайшла і виправила помилку у власному seed-скрипті: для адміністратора за замовчуванням я використала email у домені `.local`, який валідатор email вважає службовим, тож увійти під ним було б неможливо. Тепер email адміністратора можна задати змінною середовища, а за замовчуванням використовується `example.com`.

З обмежень: лічильники ліміту запитів зберігаються в пам'яті процесу, тому вони не працюватимуть при кількох копіях сервера, а токени поки що передаються лише в заголовку, без httpOnly-кукі. Відновлення пароля через email, двофакторну автентифікацію та OAuth я не робила. Також у проєкті 43 автоматичні тести, і вони працюють на SQLite в пам'яті, тому поведінку блокування рядків (`FOR UPDATE`) я перевіряла лише на рівні коду, а на справжній PostgreSQL її ще варто перевірити.
