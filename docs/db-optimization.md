# Оптимізація запитів до БД

## Як шукати повільні запити

1. Сервер сам пише в лог попередження `Повільний запит (N мс): <SQL>` для кожного запиту довше за `SLOW_QUERY_MS` (200 мс за замовчуванням; для експерименту поставте 1).
2. Знайдений запит аналізують через `EXPLAIN (ANALYZE, BUFFERS)` у `psql` або pgAdmin. Подивіться, чи це `Seq Scan` (читання всієї таблиці), чи `Index Scan`.
3. Порівняння з індексами та без них для ключових запитів автоматизовано: 
   ```bash
   python -m scripts.seed && python -m scripts.seed_demo --weeks 104
   python -m scripts.explain
   ```
   Скрипт друкує час виконання з індексами та без них (вимикає індексне сканування лише в межах транзакції). **Числа з нього заносьте у звіт**: у документі їх немає навмисно, бо вони залежать від вашої машини й обсягу даних. На малій таблиці планувальник і так може обрати `Seq Scan`: чим більше рядків, тим помітніша різниця.

## Індекси, додані в лабораторній 3

| Індекс | Запит, який він обслуговує |
|---|---|
| `bookings (bay_id, scheduled_at, ends_at)` | перевірка перетину слотів на посту при створенні запису |
| `bookings (status, scheduled_at)` | список записів адміністратора з фільтром за статусом і датою |
| `bookings (scheduled_at)` | аналітика завантаженості: усі записи за період |
| `notifications (user_id, is_read, created_at)` | «мої непрочитані, найновіші зверху» |
| `events (room, id)` | відновлення пропущених подій: кімната й номер більше за останній |
| `events (created_at)` | прибирання старих подій |

Складені індекси мають значення порядку колонок: спочатку колонки з умовою рівності (`user_id`, `room`, `bay_id`), потім діапазон чи сортування. Ціна індексів: повільніший запис і додаткове місце, тому індексуємо лише ті колонки, що справді беруть участь у запитах.

## Проблема N+1

Список записів потребує послуг кожного запису. Без підготовки це 1 запит на записи + N запитів на послуги. У `booking_query()` використано `selectinload`: послуги всіх записів сторінки підтягуються одним додатковим запитом, тож їх кількість не залежить від розміру сторінки.

## Кешування

- Активні правила знижок (`pricing_service.active_rules`) читаються при кожному перегляді слотів і створенні запису. Вони кешуються на `CACHE_TTL_SECONDS` (60 с) у пам'яті процесу й **скидаються при будь-якій зміні правил** (створення, зміна, видалення, автоматичне застосування).
- Результат аналітики завантаженості (важкий запит по всій історії) кешується на 5 хвилин, скидається після застосування автоматичних правил.
- Кеш зберігає прості незмінні об'єкти (`RuleData`), а не об'єкти SQLAlchemy: ті прив'язані до сесії, яка вже закрита.

## Пул з'єднань

`DB_POOL_SIZE` і `DB_MAX_OVERFLOW` задають розмір пулу. На безкоштовних базах ліміт з'єднань малий, тому значення краще зменшити (наприклад, 3 та 2). `pool_pre_ping` перевіряє з'єднання перед використанням.
