# Carwash Booking API

Бекенд вебсервісу для запису на автомийку та детейлінг. Це серверна частина, яку я роблю в межах лабораторних робіт з вебпрограмування, а потім використаю в курсовій і кваліфікаційній роботах.

## Що вміє (лабораторні 1 і 2)

- каталог послуг, пости, автомобілі клієнтів, користувачі з ролями (клієнт / майстер / адміністратор);
- запис на **кілька послуг одним візитом** (зв'язок M:N), тривалість і вартість рахуються автоматично;
- автоматичний підбір вільного поста й захист від подвійного бронювання;
- пошук вільних слотів на дату;
- статуси запису з контролем дозволених переходів;
- пагінація, пошук і фільтри у списках, єдиний формат помилок, авто-документація API.

Лабораторна 2 додає:

- реєстрацію та вхід (JWT: короткий access-токен + refresh-токен із ротацією й відкликанням), зміну пароля, Argon2id;
- ролі (клієнт / майстер / адміністратор) і перевірку прав у кожному ендпоїнті, у тому числі «клієнт бачить лише своє»;
- файловий сервіс: одиночне й множинне завантаження, перевірка типу, розміру та вмісту (магічні байти), заміна й видалення;
- журнал дій (`/api/audit-logs`) і обмеження частоти запитів;
- **«розумні ціни»**: адміністратор задає знижки на тихі години, а клієнт бачить ціну зі знижкою просто в списку вільних слотів.

Сповіщення в реальному часі та автоматичний розрахунок тихих годин за історією записів — у лабораторній 3.

## Стек

Python 3.12 · FastAPI · SQLAlchemy 2 · Alembic · PostgreSQL 16 · Pydantic 2 · PyJWT · Argon2id (argon2-cffi) · pytest

> Методичка написана під Node.js + Express + Prisma, тому я використовую Python-відповідники: FastAPI замість Express, SQLAlchemy + Alembic замість Prisma, Pydantic замість ручної валідації.

## Запуск

```bash
git clone <посилання на репозиторій>
cd carwash-booking-api

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env             # за потреби підправити значення
docker compose up -d             # PostgreSQL на порту 5433

alembic upgrade head             # створити таблиці
python -m scripts.seed           # адмін, 3 пости, 14 послуг, правила знижок (необов'язково)

uvicorn app.main:app --reload
```

- Swagger UI: http://localhost:8000/docs
- ReDoc: http://localhost:8000/redoc
- Перевірка стану: http://localhost:8000/health

Нова міграція після зміни моделей: `alembic revision --autogenerate -m "опис"`, перегляньте створений файл і виконайте `alembic upgrade head`.

Адмін із seed: `admin@example.com` і пароль зі змінної `SEED_ADMIN_PASSWORD`. У Swagger натисніть **Authorize** і введіть ці дані (в полі username — email), щоб пробувати захищені ендпоїнти.

## Основні ендпоїнти

Усі, крім `/health`, мають префікс `/api`. Повний перелік зі схемами — у Swagger. Стовпець «Доступ»: 🌐 без токена · 👤 будь-який автентифікований · 🛠 адмін і майстер · 🔑 лише адмін.

| Ресурс | Ендпоїнти | Доступ |
|---|---|---|
| `/auth` | `POST /register`, `/login`, `/refresh`, `/logout`, `/token` (форма для Swagger) | 🌐 |
| `/auth` | `GET /me`, `POST /change-password` | 👤 |
| `/users` | `GET /{id}`, `PATCH /{id}` (власний профіль) | 👤 |
| `/users` | `POST`, `GET` (список, пошук, `role`), `DELETE /{id}`, `PATCH` будь-якого | 🔑 |
| `/cars` | CRUD, `GET` фільтри `owner_id`, `search`; клієнт працює лише зі своїми | 👤 |
| `/services` | `GET`, `GET /{id}` | 🌐 |
| `/services` | `POST`, `PATCH`, `DELETE` | 🔑 |
| `/bays` | `GET`, `GET /{id}` | 🛠 |
| `/bays` | `POST`, `PATCH`, `DELETE` | 🔑 |
| `/bookings/availability` | `GET ?date=РРРР-ММ-ДД&service_ids=1` — слоти з цінами та знижками | 🌐 |
| `/bookings` | `POST`, `GET` (клієнт бачить свої, майстер — призначені), `GET /{id}` | 👤 |
| `/bookings/{id}/status` | `PATCH`: клієнт — лише скасувати своє, майстер — розпочати/завершити своє | 👤 |
| `/bookings/{id}` | `PATCH` (призначити майстра), `DELETE` (лише скасований) | 🔑 |
| `/pricing-rules` | CRUD правил знижок («тихі години») | 🔑 |
| `/files` | `POST /upload`, `POST /upload-multiple`, `GET`, `GET /{id}`, `GET /{id}/content`, `PUT /{id}`, `DELETE /{id}` | 👤 |
| `/audit-logs` | `GET` (фільтри `user_id`, `action`, `entity`) | 🔑 |

Списки віддають `{ items, total, page, limit, pages }`, параметри `page` та `limit` (до 100).

## Автентифікація

1. `POST /api/auth/login` повертає `{ user, tokens: { access_token, refresh_token, token_type, expires_in } }`.
2. Access-токен (15 хв) передається в заголовку `Authorization: Bearer <токен>`.
3. Коли він спливе, `POST /api/auth/refresh` з refresh-токеном (7 днів) видає нову пару, а старий refresh-токен відкликається. Якщо відкликаний токен пред'явлено повторно, сервер вважає це викраденням і скасовує всі токени користувача.
4. `POST /api/auth/logout` відкликає refresh-токен, `POST /api/auth/change-password` — усі.

Refresh-токени зберігаються в БД лише як SHA-256 хеш.

## «Розумні ціни»

Адміністратор створює правила: діапазон годин, день тижня (або щодня) і знижка до 50%. Приклад: «Тихий вівторок», вівторок 13:00–17:00, −15%.

- `GET /api/bookings/availability` для кожного слота повертає `base_price`, `price`, `discount_percent` та `rule_name`;
- коли клієнт обирає слот, запис отримує знижку автоматично, а її розмір зберігається в записі (`discount_percent`), тож зміна правил не чіпає старі записи;
- якщо слот підпадає під кілька правил, діє одна, найбільша знижка (вони не складаються);
- кінець діапазону не входить: правило 13:00–17:00 діє для слота 16:30, але не для 17:00.

## Формат помилок

```json
{ "error": "Обраний пост у цей час уже зайнятий" }
```

Помилки валідації (422) додатково мають `details` зі списком полів. Коди: 401 — немає або недійсний токен, 403 — недостатньо прав, 404 — не знайдено, 409 — конфлікт (дублікат, зайнятий слот, недозволений перехід статусу), 413 — файл завеликий, 422 — порушено правило (минулий час, не робочі години, чужий автомобіль, непідтримуваний файл), 429 — забагато запитів (заголовок `Retry-After`).

## Правила запису

- час передається **з часовим поясом** (`2026-10-25T10:00:00+03:00`);
- запис має повністю вміщатися в робочий день (за замовчуванням 9:00–20:00, змінюється в `.env`);
- пост обирається автоматично або вказується явно; перетин за часом на одному посту неможливий;
- ціна й тривалість послуг фіксуються в записі на момент створення;
- статуси: `planned → in_progress → done`, скасувати можна з `planned` та `in_progress`.
